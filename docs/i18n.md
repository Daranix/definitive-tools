# Internationalisation (i18n)

The application ships in **English** (default) and **Spanish**, using
[`@ngx-translate/core`](https://github.com/ngx-translate/core) with translation
bundles compiled into the application at build time (no HTTP round trip, so SSR
and prerendering stay consistent). English is bundled inline with the initial
chunk, and every other language is a lazily imported chunk that is loaded (and
awaited) before the first render, so visitors never download copy for a
language they do not use.

## URL strategy

| Language | Home | Tool | Legal |
| --- | --- | --- | --- |
| English (default) | `/` | `/tool/qr-generator` | `/legal/privacy` |
| Spanish | `/es` | `/es/tool/qr-generator` | `/es/legal/privacy` |

English never carries a prefix. Every other language is mounted as a child tree
under its language code, generated in `src/app/app.routes.ts`.

`I18nService` keeps the active language in sync with the URL, persists explicit
choices in `localStorage`, sets `<html lang>` and updates `og:locale`.

**The URL is the source of truth.** A page is English when its path has no
language prefix and Spanish when it starts with `/es`; the browser language is
never sniffed, so a shared link always opens in the language it was shared in.
The only exception is the bare home URL (`/`): if the visitor previously chose
Spanish, `/` redirects to `/es`, so returning visitors do not fall back into
English.

## File layout

```
src/app/i18n/
  languages.ts                 # language list, URL helpers
  i18n.service.ts              # active language, t(), Intl formatting
  i18n.providers.ts            # provideI18n()
  messages/en/<namespace>.json # hand written fragments (source of truth)
  messages/es/<namespace>.json
  translations/en.json         # generated, do not edit
  translations/es.json
```

`node scripts/build-i18n.mjs` merges every fragment into the generated bundles
and fails when the two languages drift apart. `translations/*.json` are
generated files: **never edit them by hand**.

Every feature owns exactly one fragment pair named after its namespace, for
example `messages/en/qr-generator.json` + `messages/es/qr-generator.json`,
whose top-level keys become `qr-generator.*`.

Verify a single fragment pair while other work is in flight:

```bash
node scripts/check-i18n-fragment.mjs <namespace>
```

## Key naming

* `namespace.section.key` — lowercase, dot separated, no spaces.
* Namespaces match the feature: `qr-generator`, `base64`, `home`, `tools`,
  `common`, `legal`, `calculators`.
* Shared, feature independent copy lives in `common` (`common.actions.*`,
  `common.nav.*`, `common.errors.*`, `common.language.*`, `common.footer.*`,
  `common.toolBar.*`). **Never add a key to `common.json` from a feature branch
  — use your own namespace instead.**
* Keys are stable identifiers. They describe meaning, not the English wording
  (`qr-generator.actions.download`, not `qr-generator.downloadButton`).

## Templates

Import the pipe in the standalone component:

```ts
import { TranslatePipe } from '@ngx-translate/core';

@Component({
  imports: [/* … */ TranslatePipe],
  // …
})
```

Then translate every user visible string:

```html
<!-- before -->
<h1>QR Code Generator</h1>
<input placeholder="Enter the URL">

<!-- after -->
<h1>{{ 'tools.qr-generator.name' | translate }}</h1>
<input [placeholder]="'qr-generator.fields.urlPlaceholder' | translate">
```

Attribute bindings, `title`, `aria-label` and `alt` follow the same pattern:

```html
<button [attr.aria-label]="'qr-generator.actions.reset' | translate" [title]="'qr-generator.actions.reset' | translate">
```

### Interpolation

```json
{ "resultSaved": "Saved {{ count }} characters" }
```

```html
{{ 'qr-generator.messages.resultSaved' | translate: { count: value().length } }}
```

### Plurals

`ngx-translate` has no ICU plural support. Prefer wording that works in both
counts, or branch explicitly:

```html
@if (files.length === 1) {
  {{ 'ns.messages.oneFile' | translate }}
} @else {
  {{ 'ns.messages.manyFiles' | translate: { count: files.length } }}
}
```

## TypeScript

Inject the service and read strings through `t()`. It reads the language signal
internally, so it stays reactive inside `computed()` and `effect()`:

```ts
import { I18nService } from '@/app/i18n/i18n.service';

private readonly i18n = inject(I18nService);

// Labels, options, messages produced in code
readonly formats = computed(() => [
  { value: 'png', label: this.i18n.t('image-converter.formats.png') },
]);

// Toasts, errors, confirmations
this.toastService.success({ message: this.i18n.t('qr-generator.messages.copied') });
```

Rules:

* A `computed()` or template bound field must not read a string captured
  outside a signal, otherwise it will not update on language change. Always call
  `this.i18n.t(...)` **inside** the `computed()`.
* Plain class fields that hold copy (e.g. `readonly title = 'Image Converter'`)
  become `readonly title = computed(() => this.i18n.t('image-converter.title'))`
  and the template calls `title()`.
* `const` lists of labels declared at module scope inside a page file should
  become a `computed()` in the component, or be replaced by a key list plus
  `t()` lookups.
* Never translate code identifiers, storage keys, MIME types, file extensions,
  format names (`PNG`, `JPEG`, `WAV`), protocol names (`JWT`, `Base64`, `API`,
  `JSON`, `Markdown`, `Swagger`, `Open Graph`), unit symbols or brand names.
  Those stay identical in both bundles.

## Router links

Every internal link must be language aware, otherwise it drops the `/es`
prefix. Import `LocalizeUrlPipe` and use it on `routerLink` values:

```ts
import { LocalizeUrlPipe } from '@/app/pipes/localize-url.pipe';

@Component({ imports: [/* … */ LocalizeUrlPipe] })
```

```html
<!-- before -->
<a routerLink="/">Home</a>
<a [routerLink]="['/tool', tool.id]">Open</a>

<!-- after -->
<a [routerLink]="'/' | localizeUrl">{{ 'nav.home' | translate }}</a>
<a [routerLink]="['/tool', tool.id] | localizeUrl">…</a>
```

Use `[routerLink]` (property binding) whenever a pipe is applied.

## Numbers, currencies and dates

Do not hardcode `Intl.NumberFormat('es-ES')` or `toLocaleString('es-ES')`.
Use the helpers on `I18nService`, which follow the active language:

```ts
this.i18n.formatNumber(1234.5);                       // 1,234.5 | 1.234,5
this.i18n.formatCurrency(1234.5);                     // €1,234.50 | 1.234,50 €
this.i18n.formatPercent(0.21);                        // 21% | 21 %
this.i18n.formatDate(new Date(), { dateStyle: 'long' });
```

Shared calculator formatting lives in
`src/app/pages/calculator/shared/calculator-format.ts`; extend it rather than
duplicating `Intl` calls.

## Metadata

SEO strings live in each namespace (`<namespace>.seo.title`,
`.seo.description`, `.seo.keywords`) and are pushed through `MetadataService`:

```ts
constructor() {
  this.updateMetadata();
  effect(() => {
    this.i18n.language();
    this.updateMetadata();
  });
}

private updateMetadata(): void {
  this.metadataService.updateMetadata({
    title: this.i18n.t('qr-generator.seo.title'),
    description: this.i18n.t('qr-generator.seo.description'),
    keywords: this.i18n.t('qr-generator.seo.keywords'),
  });
}
```

## Adding a language

1. Add the code to `SUPPORTED_LANGUAGES` in `src/app/i18n/languages.ts` (plus
   labels and locale).
2. Add `messages/<lang>/` fragments and run `node scripts/build-i18n.mjs`.
3. Add a branch for the new code in `StaticTranslateLoader`
   (`src/app/i18n/i18n.providers.ts`) that dynamically imports
   `translations/<lang>.json`, and add the code to `addLangs([...])`.

## Verifying a deployment

`node scripts/smoke-i18n.mjs` (against a running server, `SMOKE_BASE` defaults
to `http://127.0.0.1:4321`) renders every route in both languages over SSR and
fails if a page has the wrong `<html lang>`, falls back to the generic site
title, or leaks a raw translation key into the markup.

## Checklist for a translated feature

- [ ] Every user visible string comes from a key (search the template for raw text).
- [ ] `TranslatePipe` / `LocalizeUrlPipe` imported by every touched component.
- [ ] `routerLink` values wrapped with `localizeUrl`.
- [ ] `node scripts/check-i18n-fragment.mjs <namespace>` passes.
- [ ] `npx tsc -p tsconfig.app.json --noEmit` reports no error in touched files.
- [ ] No behavioural change: ids, `data-testid`, classes and logic untouched.
